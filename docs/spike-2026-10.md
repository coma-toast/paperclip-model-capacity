# Spike: host behaviors the plugin depends on

Paperclip `2026.1026.0-nightly.0`. Checked 2026-10-28 on a live instance with throwaway tasks, all cancelled afterwards.

## Part 1: REST checks (done)

| # | Check | Result | Plan impact |
|---|---|---|---|
| 1a | Assign a task that has an open (not `done`) blocker | **No run created**: the assignment wake is skipped | Proactive blockers gate runs (C1). |
| 1b | Same, without a blocker (control) | Run queued | Confirms 1a is the blocker's effect. |
| 1c | Board user (human) comment on a blocked task | Run queued | Human comment wakes bypass the gate; count them as over-limit (B4). |
| 1d | Remove the blocker without closing it | **No wake** | Release must call `requestWakeup` after `removeBlockers` (C3). |
| 1e | Mark the blocker `done` | Run queued automatically (`automation`, blockers-resolved wake) | The queue blocker must never be closed `done` (risk 3). |
| 2r | `PATCH /api/issues/:id` with `assigneeAdapterOverrides` (board token) | Persists | REST fallback for overflow works (D2). |

Also seen: Paperclip's built-in queue started older queued runs before a newer `high` priority one, so its queue doesn't order by priority. The plugin's ordering (C2) is needed.

## Part 2: plugin SDK checks (pending)

`scripts/spike/` is a throwaway plugin whose `spike` data handler checks:
- the SDK gate (`relations.addBlockers` + assign → no run);
- `requestWakeup` while blocked (expected to throw);
- `removeBlockers` + `requestWakeup` (expected `{queued, runId}`);
- `assigneeAdapterOverrides` through `ctx.issues.update`;
- reading `heartbeat_runs` through `database.coreReadTables`.

Build: `node scripts/spike/build.mjs`. Install from a local path, call `POST /api/plugins/<id>/bridge/data` with `{"key":"spike","params":{"companyId":"…","agentId":"…"}}`, then uninstall.
