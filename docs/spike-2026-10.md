# Spike: host behaviors the plugin depends on

Paperclip `2026.1026.0-nightly.0`. Checked 2026-10-28 on a live instance with throwaway tasks, all cancelled afterwards.

## Part 1: REST checks (done)

| # | Check | Result | Plan impact |
|---|---|---|---|
| 1a | Assign a task that has an open (not `done`) blocker | **No run created**: the assignment wake is skipped | Proactive blockers gate runs (C1). |
| 1b | Same, without a blocker (control) | Run queued | Confirms 1a is the blocker's effect. |
| 1c | Board user (human) comment on a blocked task | Run queued | Human comment wakes bypass the gate; count them as over-limit (B4). |
| 1d | Remove the blocker without closing it | **No wake** | Release must call `requestWakeup` after `removeBlockers` (C3). |
| 1e | Mark the blocker `done` | Run queued automatically (`automation`, blockers-resolved wake) | The queue blocker must never be closed `done` (risk 3). |
| 2r | `PATCH /api/issues/:id` with `assigneeAdapterOverrides` (board token) | Persists | REST fallback for overflow works (D2). |

Also seen: Paperclip's built-in queue started older queued runs before a newer `high` priority one, so its queue doesn't order by priority. The plugin's ordering (C2) is needed.

## Part 2: plugin SDK checks (done)

Ran the throwaway plugin in `scripts/spike/` on the same instance, then uninstalled it. Its two test tasks were cancelled.

| # | Check | Result | Plan impact |
|---|---|---|---|
| 4 | `ctx.db.query` on `public.heartbeat_runs` with `database.coreReadTables: ["heartbeat_runs"]` | **Works**: grouped counts by status, and runs for one issue via `context_snapshot->>'issueId'` | B2 counts and N4 restart rebuild can read runs directly. |
| 1s | `relations.addBlockers` through the SDK, then assign | **No run** | The SDK can gate tasks the same way REST can (C1). |
| 1w | `requestWakeup` while blocked | Throws `Issue is blocked by unresolved blockers` | Always remove the blocker before waking (C3). |
| 2 | `relations.removeBlockers` + `requestWakeup` | Returns `{queued: true, runId}`, and the run is queued | The release path works. Store `runId` as released-not-started (B2). |
| 3 | `ctx.issues.update` with `assigneeAdapterOverrides` (cast; not in the SDK's TS type) | **Persists** (read back) | Overflow (D2) can use the SDK, so the REST board token is only a fallback. |

**Database declaration gotchas**:
- `migrationsDir` is required.
- Every migration statement must name the plugin's schema: `plugin_<slug>_<first 10 hex of sha256(pluginKey)>`, where the slug is `namespaceSlug` or the plugin key, lowercased, with non-alphanumerics replaced by `_`, max 36 chars.
- Destructive statements (`DROP`, `TRUNCATE`, `DELETE`) are rejected.

**Install gotcha:** copying a plugin folder from macOS with `tar` adds `._*` files. A `._001_init.sql` file in `migrations/` would be read as a migration, so strip them (`COPYFILE_DISABLE=1 tar …`).

## Fallbacks
- Status-based holds as well as blockers: **not needed**.
- REST board token for overrides: **not needed** (keep it as an optional fallback).
- `Issue.activeRun` instead of `heartbeat_runs`: **not needed**.
